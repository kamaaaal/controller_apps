# Taste
- Wants important project details and every change made documented in the project's `spec/` folder (e.g. per-iteration markdown files plus updating the plan and known-issues docs). Also expects idea/backlog lists captured in their own repo-root markdown file (e.g. `up_games.md`) alongside the spec docs. Confidence: 0.75
- When asking for a prompt to hand to another (stronger) agent, wants the prompt text alone and no execution — explicitly says not to do anything else. Confidence: 0.6
- When asking for a prompt to hand to another (stronger) agent, prefers it persisted as a markdown file in the repo (e.g. design.md) rather than only output in chat. Confidence: 0.5
- Prefers a colorful, neon arcade aesthetic over flat/plain dark UI. Confidence: 0.6
- Wants Xbox-forward branding/colors as the dominant palette, with only light PlayStation accents. Confidence: 0.6
- Likes decorative controller icon artwork placed subtly in the background. Confidence: 0.5
- Wants accessibility to be improved/hardened (e.g. WCAG-level contrast, focus, reduced motion), not just noted. Confidence: 0.6
- Prefers modern frosted-glass / blurred-gradient surfaces (glassmorphism) with minimal hairline borders over solid neon outlines. Dislikes visible rectangular "container div" panels as cliché — wants organic, soft-edged glass that dissolves into the page (e.g. mask-faded edges) rather than boxed shapes. Confidence: 0.6
- Wants visual consistency across similar screens: if one screen has decorative flourishes (e.g. background controller art), wants them on all comparable screens, not just one. Confidence: 0.6
- Likes ambient/decorative UI to be dynamic and input-reactive — e.g. background icons that parallax and glow in response to live joystick movement, not static art. Confidence: 0.6
- Prefers adopting established libraries/frameworks instead of hand-rolling (e.g. React Router for routing, Phaser or motion/react for a game engine / UI animation). Explicitly questioned writing raw Canvas code when a library would reduce complexity and be reusable across upcoming games — favors solutions that pay off across future work over one-off native implementations. Confidence: 0.7
- Wants strict layering for modals/overlays so they never overlap or stack wrongly, with an explicit documented z-index scale. Confidence: 0.5
- Wants navigation to guard against stray or still-held controller input (input lock-out after transitions; only the back button exits a result screen, not confirm). Confidence: 0.5
- Dislikes primary screens (e.g. the home/library game grid) being cramped or requiring scrolling — wants all items visible in the viewport without scroll, and is happy to drop container panels entirely for a transparent, full-bleed, wide layout to achieve that. Confidence: 0.6
- Values game concepts that train muscle memory, reflexes and puzzle-solving, and wants a diverse skill mix across the library (memory, precision, coordination, spatial reasoning, rhythm) instead of more clones of the same reflex game. Confidence: 0.7
- Given a scope choice between a conservative patch and a full root-cause refactor, picks the ambitious option (engine seam refactor over "bug fixes only") and expects the agent to execute the whole change set end-to-end without further check-ins — e.g. unify the shared game loop's timestep and renderer rather than special-casing each game individually. Confidence: 0.8
- When asked to improve an app, expects a proactive sweep: find and fix ALL issues discovered (UI collisions/overlaps, dead code, architecture seams), not just the ones explicitly reported. Confidence: 0.8
- Verifies changes end-to-end in a real browser driving a synthetic gamepad (exercising actual input paths and screenshots), rather than relying on unit tests alone. Confidence: 0.8
- Plays with a real 8BitDo Ultimate 2C Wireless controller whose D-pad reports at non-standard button indices; treats controller input quirks as genuine bugs to fix (and wants diagnostic tooling for non-standard pads) rather than as acceptable edge cases. Confidence: 0.6
- For device/hardware quirks, prefers self-calibrating, verifiable handling over hard-coded per-device tables: ship a calibration wizard that captures the real values from the user's own device plus a live diagnostics monitor, and never ship guessed magic numbers as the only path — always give an in-app way to correct them. Specifically distrusts published reverse-engineering tables (they can be wrong — e.g. a controller's published axis order was swapped) in favour of the player's own measured data. Confidence: 0.9
- Once real device data has been captured, wants the corrected values baked into the shipped default profile (so every user benefits), not just left in that one user's local calibration. Confidence: 0.8
- Wants guards so a wrong hardware mapping assignment degrades safely — ignore/no-op the bad input rather than letting it surface as a confusing symptom (e.g. a direction stuck on). Confidence: 0.8
- For diagnosing hardware quirks, wants the raw captured data to be copyable/exportable so values can be inspected, shared or pasted into an issue outside the app. Confidence: 0.75
- Wants gamepad focus navigation to be screen-type aware: forms (e.g. settings) navigate up/down in reading order one field at a time and must never skip a control, while grid/card layouts keep spatial navigation. Confidence: 0.85
- Wants focus-candidate alignment matched by box span overlap rather than centre distance, so wide and narrow controls in the same column still count as the same row. Confidence: 0.8
